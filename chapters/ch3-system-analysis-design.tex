\proposalchapter{System Analysis and Design}

The purpose of system analysis and design is to systematically create effective and efficient solutions to meet specific business or organizational needs[cite: 2]. System analysis is conducted to study a system and its components in order to identify core objectives, specify functional requirements, and define system boundaries[cite: 2].

\section{System Analysis}

The proposed Nepal Bus Ticket Booking System will be built following the structured approach to software development. The structured approach provides a step-by-step, process-driven methodology that focuses on data flow, system decomposition, and structured data modeling. System Analysis will evaluate the operational, functional, and technical requirements of the system using tools such as Data Flow Diagrams (DFDs), Entity-Relationship Diagrams (ERDs), and Data Dictionaries to ensure a clear separation of data and process logic before implementation.

\subsection{Requirement Analysis}

Requirement analysis defines the functional and non-functional requirements of the proposed system. Figure~\ref{fig:contextdiagram} shows the Context Diagram (Level 0 DFD) of the Nepal Bus Ticket Booking System, which establishes the system boundary and models high-level interactions between external entities and the system.

	\label{fig:contextdiagram}

The system identifies four primary external entities:
\begin{itemize}
	\item \textbf{Passenger:} Searches for bus trips, selects seats with temporary holds, initiates online payments, receives booking confirmations, and requests cancellations.
	\item \textbf{Bus Operator:} Configures fleet details, seat layouts, routes, schedules, dynamic fare rules, and views booking reports for their fleet.
	\item \textbf{Administrator:} Approves new bus operators, manages user accounts, and monitors system-wide analytics.
	\item \textbf{eSewa Gateway:} External payment gateway integrated to verify transactions securely.
\end{itemize}

\textbf{i. Functional Requirements}

\textit{Passenger}
\begin{enumerate}
	\item Register, log in, and log out securely.
	\item Search for buses by origin, destination, and travel date, and sort results by price or departure time.
	\item View the seat map of a bus and select available seats.
	\item Enter passenger details and pay online through eSewa.
	\item View booking confirmations and booking history.
	\item Cancel a booking according to system cancellation rules.
\end{enumerate}

\textit{Bus Operator}
\begin{enumerate}
	\item Log in to an operator account.
	\item Add and manage buses, including bus types and seat layouts.
	\item Add and manage routes, schedules, and fares (including peak-season pricing).
	\item View bookings and reports for their own buses.
	\item Cancel scheduled trips when necessary.
\end{enumerate}

\textit{Administrator}
\begin{enumerate}
	\item Log in to an administrator account.
	\item Approve and manage bus operators.
	\item Manage user accounts, including account suspension.
	\item View all system-wide bookings and reports.
\end{enumerate}

\textit{System}
\begin{enumerate}
	\item Prevent double booking by holding selected seats temporarily during checkout.
	\item Calculate fares based on base route pricing and active fare rules.
	\item Confirm bookings only after successful payment verification with eSewa.
	\item Enforce role-based access control across all features.
\end{enumerate}

\textbf{ii. Non-Functional Requirements}
\begin{enumerate}
	\item \textit{Security:} Store passwords in hashed form; restrict access using role-based permissions.
	\item \textit{Data Integrity:} Ensure atomic transactions for bookings, seat locks, and payments.
	\item \textit{Usability:} Responsive and simple interface accessible via mobile and desktop browsers.
	\item \textit{Performance:} Rapid seat map rendering and search result response times.
	\item \textit{Maintainability:} Modular codebase structured for future extensibility.
	\item \textit{Compatibility:} Full support across modern web browsers.
\end{enumerate}

\subsection{Feasibility Analysis}

A feasibility study determines whether the proposed system can be successfully developed and deployed using available technical skills, time, and resources.

\subsubsection{Technical Feasibility}
The system will be built using open-source technologies: Next.js and Tailwind CSS for the user interface, NestJS for the server (written in TypeScript), and PostgreSQL for relational data storage. PostgreSQL's support for ACID transactions and row-level locking directly enables the seat-locking mechanism required to prevent concurrent double bookings. Payment integration will utilize the eSewa ePay sandbox environment for secure transaction processing. Git and GitHub will handle version control. The technical risk involved in seat concurrency will be mitigated using database row-level locking during simultaneous booking requests. Therefore, the project is technically feasible.

\subsubsection{Operational Feasibility}
The proposed system replaces physical ticket counters and phone calls with a streamlined online workflow: search, select seat, and pay. Passengers require only a modern web browser and internet connection. Operators and administrators receive dedicated web-based dashboards to manage fleets, routes, schedules, and analytics, reducing paper-based record-keeping. The system is operationally feasible.

\subsubsection{Economic Feasibility}
All core frameworks and development tools (Next.js, NestJS, PostgreSQL, Tailwind CSS, Git) are free and open-source, eliminating software licensing costs. Payment processing during development utilizes the free eSewa sandbox testing suite. The primary resource investment is development time, while operational benefits include reduced labor overhead, automated seat management, and improved record accuracy. Thus, the system is economically feasible.

\section{High-Level Design}

Figure~\ref{fig:architecture} presents the high-level system architecture structured in three main layers alongside an external payment integration.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=\textwidth]{figures/architecture-diagram.pdf}
	\caption{High-Level Architecture of the System}
	\label{fig:architecture}
\end{figure}

The web frontend (Next.js and Tailwind CSS) acts as the client layer for passengers, operators, and administrators. The backend server (NestJS) processes REST API requests, handles authentication, applies fare rules, manages seat locking logic, and communicates with PostgreSQL for database operations. Online payment verification is managed asynchronously via eSewa API calls.
